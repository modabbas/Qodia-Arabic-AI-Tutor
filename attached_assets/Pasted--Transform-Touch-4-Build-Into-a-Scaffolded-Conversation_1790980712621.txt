# Transform Touch 4 (Build) Into a Scaffolded Conversational Flow

## Context
Students currently freeze at Touch 4 — they see a blank code box with a formal "اللمسة ٤ - بناء" header and close the page without attempting anything. This is "blank page syndrome" combined with exam-like framing. This task redesigns Touch 4's presentation and interaction flow WITHOUT changing the underlying validation logic (Levels 1/2/3) or the Hints system — those stay exactly as already built.

Note: This REPLACES the earlier "warmup-exercise" concept entirely — do not implement a separate warm-up step before Touch 4. Instead, Touch 4 itself is restructured internally as described below.

## The New Flow (4 sub-steps inside what is still called Touch 4)

### Sub-step A: Conversational framing (visual only)
Replace the formal "اللمسة ٤ - بناء" exam-style header and plain task description with a chat-bubble style presentation:
- Mentor avatar/icon + chat bubble containing the task, phrased conversationally (e.g., "طيب، جرّب تضيف useState هون 👇" instead of a formal instruction paragraph)
- Keep the same underlying task description content already generated by Gemini — just restyle the presentation container as a chat bubble instead of a formal card
- This is purely a UI/CSS change, reuse existing task text from the session generation response, just wrap it differently

### Sub-step B: Multiple-choice "first move" question (new, before any typing)
Before showing the code input, show a small multiple-choice question asking what the FIRST logical step is. This requires Gemini to generate 2-3 plausible options (one correct) as part of the existing touch4_build generation.

Add this to the existing Gemini prompt that generates touch4_build:

```
أضف أيضاً حقل "first_move_choice" لنفس touch4_build:

"first_move_choice": {
  "question_ar": "شو أول شي لازم تعمل؟",
  "options": [
    { "id": "a", "text_ar": "أعرّف متغير الحالة باستخدام useState", "correct": true },
    { "id": "b", "text_ar": "أستدعي API مباشرة", "correct": false },
    { "id": "c", "text_ar": "أكتب شرط if بالبداية", "correct": false }
  ],
  "scaffold_code_on_correct": "const [isOpen, setIsOpen] = useState("
}
```

قواعد:
- خيار واحد صح وخيارين غلط منطقيين (مش سخيفين)
- scaffold_code_on_correct هو الجزء الأول من الكود اللي بينكشف تلقائياً لما يختار صح
- لا تكشف الفراغ الأخير (القيمة أو باقي السطر) — هذا يبقى للطالب يكمله

Student picks an option:
- Correct → brief positive micro-feedback, then the `scaffold_code_on_correct` text appears pre-filled in the code area (read-only prefix, styled slightly muted/locked) with the cursor positioned right after it for the student to continue typing
- Incorrect → gentle inline message ("قريب! فكّر تاني") with the option disabled, student tries another option (no XP penalty, no attempt counter impact — this is pre-task scaffolding, not graded)

### Sub-step C: Completion with minimal typing
The code area now shows:
- The scaffolded prefix (from the correct choice) as locked/muted text
- An empty editable continuation where the student types the rest

This reuses the EXISTING Level 1/2/3 validation and Hints system exactly as already built — validation runs on the FULL code (prefix + student's typed continuation combined), no changes to validation logic itself.

### Sub-step D: Progressive reduction of scaffolding per concept mastery
When the student encounters the SAME concept again later (a review session, per Learning Path's spaced repetition), reduce scaffolding:
- First encounter of a concept: multiple-choice first-move + prefix shown (as above)
- Review encounter (mastery already >= 70 from before): skip the multiple-choice, show a shorter prefix (just first few characters, not full first line)
- Third+ encounter / high mastery (>= 90): no scaffolding at all, blank box as before (student is ready)

Use the existing `mastery_score` and concept repeat tracking already in the Learning Path `learning_map` table to decide which tier to show — no new database fields needed, just read existing mastery data before rendering Touch 4.

## What NOT to Do
- Do NOT touch Level 1/2/3 validation logic — it already validates the full submitted code correctly regardless of how much was pre-filled
- Do NOT touch the Hints system (still unlocks after failed full-code submission attempts, as already built)
- Do NOT add XP penalty or attempt-counter impact to the multiple-choice first-move question — it's free scaffolding, not graded
- Do NOT implement a separate warm-up screen before Touch 4 — this replaces that idea entirely, scaffolding happens INSIDE Touch 4
- Do NOT change Touch 1, 2, 3, or 5
- Do NOT add a new Gemini API call — the first_move_choice field is generated in the SAME call that already generates touch4_build
